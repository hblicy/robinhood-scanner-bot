# EVM RPC 服务端额度与候选分流实施计划

## 目标

在不改变评分、Telegram 推送和安全门槛的前提下，让 Ethereum、Base、BSC、Robinhood 只对可能产生有效通知或风险取证的 V2 候选使用分析 RPC。四链使用同一个 Dwellir 扫描器专用 Key，20M 月度硬上限由 Dwellir 控制台执行。

## 执行顺序

1. 运行当前完整测试，确认基线。
2. 在评分模块增加只使用候选与 Gecko 数据的保守最高分计算；缺失或非法数据返回 unknown。
3. 让 EVM 安全注册表公开场所是否支持严格卖出验证，并增加统一候选门控：不支持场所直接去重，V2 上界低于 `max(0, MIN_SCORE - 10)` 才跳过。
4. Robinhood 的逐候选 Pons 身份读取固定使用官方 discovery primary，不回退分析节点；可恢复错误继续进入已有持久化恢复。
5. 将同一候选门控接入 Robinhood 实时/补扫/恢复路径和通用 EVM runner。
6. 给 analysis RPC 增加 429 冷却熔断：有限重试后打开、冷却期间不深检、到期仅一次探测、成功关闭；每个熔断周期只告警一次。
7. 增加聚合路由统计：官方 Pons 检查、身份延迟、不支持场所跳过、评分上界跳过、付费深检、429 冷却跳过。
8. 更新 `.env.example` 和 README，写明四链分析 URL 必须使用同一个 20M quota 专用 Key，另一个项目使用独立 Key；无本地月额度配置。
9. 运行相关测试、完整 `npm test`、`git diff --check`，检查日志与通知不包含 RPC URL 或凭据。

## 测试驱动验收点

- Pons 身份检查只调用官方 Provider；429/超时保留为可恢复候选，永久错误向上传播。
- V3、V4、未知场所不调用完整分析；支持的 V2 仍可分析。
- 确定最高分低于深检线才跳过；等于深检线、缺失字段或非法字段都放行。
- 默认 `MIN_SCORE=70` 时，60–69 的初步候选仍进入既有风险深检。
- 实时、启动恢复和候选恢复使用相同门控。
- analysis 429 熔断不影响官方发现和游标推进；冷却期无重复分析调用，探测成功后恢复。
- 每次熔断周期最多一条 Telegram 限流告警，非 429 异常不被吞掉。
- Solana 行为不变，所有现有通知策略回归测试通过。

## 部署操作（代码不能代办）

1. 在 Dwellir 创建扫描器专用 API Key，设置 monthly quota 为 `20,000,000`。
2. Ethereum、Base、BSC、Robinhood 的 analysis/fallback URL 使用该专用 Key。
3. 另一个项目改用独立 API Key，并设置其自己的 5M quota。
4. 部署后对照 Dwellir 控制台观察 12–24 小时响应增量和本地路由统计。
