# 跨 EVM RPC 候选分流、零调用预筛与服务端月度硬预算设计

## 背景

Robinhood 扫描器已经采用“官方 RPC 发现、Alchemy 分析”的双 RPC 架构，但候选处理路径仍有两类高成本流量：

1. GeckoTerminal 返回的每个候选都会通过 Alchemy 执行 Pons 身份识别。
2. V3、V4 和未知交易场所即使当前无法验证卖出能力，也会继续通过 Alchemy 读取 ERC-20 元数据、owner、字节码等信息。

严格通知策略要求普通正向提醒同时满足最终评分门槛和 `sellability=confirmed`。当前只有受支持的 V2 场所能够完成该验证，因此上述 V3、V4 和未知场所的深检不能产生普通 Telegram 提醒，却会持续消耗 Alchemy CU。官方发现节点故障时，若逐候选身份识别也进入发现节点的全局备用路径，还可能把候选流量集中回退到 Alchemy。

本次优化目标是让付费分析 RPC 只承担可能产生有效通知或当前规则要求风险取证的候选深检，同时保持严格卖出证据门槛和现有推送规则。预算覆盖 Ethereum、Base、BSC、Robinhood 四条 EVM 链；Solana 不计入本次额度。

Dwellir Developer 套餐每月共有 25,000,000 次 API Responses，用户的另一个项目固定预留 5,000,000 次，因此本扫描器的四条 EVM 链必须共享不超过 20,000,000 次/月的硬上限。

## 方案比较

### 方案 A：身份识别分流、场所门控和安全上界预筛（采用）

- Pons 身份识别只使用官方发现 RPC，不使用 Alchemy 备用节点。
- 非 Pons 的 V3、V4 和未知交易场所完成身份识别后直接标记为已处理，不进入通用深检。
- 受支持的 V2 候选先用发现事件和 Gecko 已有市场数据计算“初步评分理论最高分”；只有仍可能达到现有深检线 `max(0, MIN_SCORE - 10)` 时才进入付费 RPC 深检。
- 市场数据不完整或无法可靠计算上界时放行到深检，避免因数据缺失漏掉候选。
- 增加按角色聚合的候选路由计数，定期输出而不逐请求打印。
- 四条 EVM 链的分析 URL 使用同一个扫描器专用 Dwellir API Key，并在 Dwellir 控制台为该 Key 设置 20,000,000 次/月服务端额度；另一个项目必须使用独立 Key。
- 分析节点连续返回 429 时，本进程暂停付费深检一段时间并继续官方发现，冷却后小流量探测恢复；每次熔断周期只发送一次 Telegram 告警。

该方案节省范围最大，同时不会放宽安全规则，也不会减少当前会进入卖出风险检查的候选范围。代价是 V3、V4 和未知场所不再生成低价值的完整终端分析日志；它们仍会被发现、完成必要的身份分流并记录为已处理。20M 硬保证由供应商按 Key 和真实账单周期执行，避免本地自然月与账单周期错位。

### 方案 B：只把 Pons 身份识别改走官方 RPC

改动最小，但大量无法通过卖出能力门槛的 V3、V4 候选仍会消耗 Alchemy 元数据调用，不能解决当前主要用量来源。

### 方案 C：固定市场阈值硬过滤

可以进一步减少 V2 深检，但固定要求市值、流动性或成交量达到某个值会改变产品筛选规则，并可能漏掉依靠年龄、社交、聪明钱或安全分达到门槛的候选。本次不采用。

## 处理流程

每个实时候选按以下顺序处理：

1. 使用官方发现 RPC 读取 Pons 身份。
2. 若确认属于 Pons，进入现有 Pons 生命周期处理，不执行通用候选分析。
3. 若身份读取发生 429、超时或网络错误，保持候选未处理并进入现有持久化延迟恢复；重试仍只使用官方 RPC。
4. 若确认不是 Pons，判断交易场所是否支持严格卖出能力检查。
5. V3、V4 或未知场所记录 `unsupported-sellability-venue` 并标记已处理，不调用 Alchemy。
6. 支持的 V2 候选计算零 RPC 评分上界。
7. 上界低于 `max(0, MIN_SCORE - 10)` 时记录 `prefilter-score-upper-bound` 并标记已处理，不调用付费 RPC。
8. 上界达到深检线或无法可靠计算时执行现有完整分析、卖出能力检查和通知决策。
9. 分析节点连续返回 429 时打开本进程分析熔断器；熔断期间记录 `analysis-rpc-cooldown` 并标记已处理，不发起付费请求，官方发现和候选去重继续运行。

启动历史补扫与实时发现共用同一候选分流逻辑，避免重启后重新产生高成本流量。已进入持久化恢复队列的候选也必须经过同样的场所门控和评分预筛。

## RPC 路由

### Pons 身份识别

候选身份识别绑定到底层官方 discovery Provider，而不是带 Alchemy 备用的发现 Session，也不是 analysis Provider。这样官方节点异常时，单次候选只延迟恢复，不会触发一段时间内全部候选身份读取改走 Alchemy。

Factory 日志、区块游标等已有链级发现请求继续使用当前双节点熔断；本次只收紧逐候选的 Pons 身份读取。链级发现完全中断时仍可按现有熔断使用 Alchemy 保持游标推进，但不会把已发现候选的高扇出身份查询一起回退。

身份查询的预期业务结果只有：

- `pons`：按 Pons 候选处理；
- `not-pons`：继续场所门控；
- 可恢复 RPC 错误：延迟重试；
- 永久校验或编程错误：保留上下文向上传播，不伪装为非 Pons。

### 付费 RPC 深检

付费分析 RPC 只接收同时满足以下条件的候选：

- 已确认不是 Pons；
- 交易场所支持当前严格卖出能力检查；
- 零 RPC 上界仍可能达到 `max(0, MIN_SCORE - 10)`，或计算上界所需数据不完整；
- 本进程分析 RPC 熔断器未处于冷却期。

进入深检后的 ERC-20 元数据、owner、字节码、V2 池验证、Transfer/Swap 证据与回执读取保持现状，不改变其 Provider 和错误语义。分析节点作为官方发现节点的熔断备用时产生的响应也由 Dwellir 对同一专用 Key 计数。

## 场所能力门控

场所是否可深检必须由卖出能力模块暴露的单一能力判断决定，候选处理器不得维护另一份易漂移的字符串列表。判断应与当前 `honeypotCheck` 支持范围一致。

目前由各 EVM 链的安全注册表或 Robinhood 兼容路径判断：

- 支持：已注册并能执行严格验证的 Uniswap V2 类场所；
- 不支持：Uniswap V3、V4 和无法匹配已注册 V2 规则的未知场所。

该门控只代表“当前实现是否能形成严格卖出证据”，不把不支持的场所描述为安全或危险，也不改变风险提醒规则。

## 零 RPC 评分上界

预筛只能使用候选事件和 Gecko 已经返回的数据，不得读取合约、Blockscout、DexScreener 或其他新增远端数据。

上界计算采用保守原则：

- 已知且不可改变的市场事实按现有评分规则计分；
- 尚未读取的链上、持仓、创建者、LP、安全和聪明钱项目按其可能获得的最高正分计入；
- 已知的硬性失败条件按现有规则处理；
- 任一参与评分的输入缺失、格式非法或无法与现有评分规则等价映射时，结果为 `unknown`，候选必须放行到深检；
- 只有确定的初步评分最高可能得分仍低于 `max(0, MIN_SCORE - 10)` 时才能跳过。该门槛与现有 `analyze` 是否执行卖出深检的判断完全一致；这样不会把原本可能进入 blocked 风险取证的 60–69 分候选提前排除。

预筛不得修改最终分数，也不得生成 Telegram 消息。通过预筛只表示“值得付费深检”，不表示安全或推荐。

为了避免评分规则出现两份实现，上界计算应复用评分模块公开的分项上限或由评分模块提供专用函数；不复制分值常量到扫描循环。

## 状态、恢复与去重

- `unsupported-sellability-venue` 和 `prefilter-score-upper-bound` 都属于已完成的静默处理结果，写入现有去重状态，防止 Gecko 每轮重新处理。
- Pons 身份的可恢复错误不得写入已处理状态，继续使用现有 2、5、10 分钟持久化恢复机制。
- 延迟恢复成功后重新从场所门控开始，不绕过预筛。
- 进程崩溃或非预期异常不得吞掉；错误必须包含候选地址和当前处理阶段。
- 不修改 `state.json` schema；若现有去重接口只保存地址，则原因仅用于日志和统计。

## 四链共享服务端月度硬预算

### 额度隔离

Dwellir 按 API Response 计费，并支持为 API Key 设置月度 quota。部署时必须创建扫描器专用 Key，在控制台把该 Key 的月度 quota 设置为 20,000,000；Ethereum、Base、BSC、Robinhood 四条链的 `ANALYSIS_RPC_URL` 和发现备用 URL 都使用这个 Key。另一个每月约 5,000,000 次调用的项目使用不同 Key，并设置独立额度。

本地程序不维护月度计数文件，也不推测 Dwellir 账单周期。真实硬上限、跨主机并发和周期重置均由 Dwellir 服务端负责，达到额度时由服务端拒绝请求。

### 429 熔断与恢复

429 既可能代表瞬时吞吐限制，也可能代表月度 quota 耗尽，程序不能仅凭状态码声称具体原因。analysis Provider 的可识别 429 在完成现有有限重试后打开进程内熔断器：

1. 当前深检保留带链、候选地址和阶段的错误上下文；
2. 后续候选在冷却期内静默标记为 `analysis-rpc-cooldown`，不进入付费深检；
3. 官方发现、Pons 身份识别、游标推进和去重继续运行；
4. 每个熔断周期只发送一次 Telegram，文案说明“分析 RPC 被限流或额度耗尽，深检暂时暂停”，不泄露 URL 或 Key；
5. 固定冷却期结束后允许一次深检探测；成功即关闭熔断，仍为 429 则重新进入冷却。

四个链进程各自熔断，因此告警可能每链各一条；服务端专用 Key 的 quota 才是四链聚合的唯一硬保证。本次不增加本地月额度配置。

## 统计与日志

在现有周期摘要中增加进程内计数：

- `pons_official_checks`：官方 RPC 身份识别次数；
- `skipped_unsupported_venue`：因场所不支持而跳过数量；
- `skipped_score_upper_bound`：因理论最高分不足而跳过数量；
- `paid_deep_checks`：真正进入付费 RPC 深检的数量；
- `deferred_pons_checks`：身份读取失败并延迟恢复的数量。
- `analysis_rpc_cooldown_skips`：分析 RPC 熔断冷却期间静默跳过的候选数量。

统计只记录次数，不记录 URL、API key 或请求正文。默认随现有 Gecko 周期摘要输出一行紧凑信息，避免每个跳过候选都产生噪声。现有 `analyzing`、风险结果和非预期错误日志保留。

这些计数用于比较优化前后的候选分流，不等同于供应商 CU 账单；README 必须明确这一点。

## Telegram 行为

以下行为保持不变：

- 普通实时候选仍需最终评分达到 `MIN_SCORE` 且 `sellability=confirmed` 才推送；
- `hard_kill`、`rescued`、`green`、`market_ready` 等重要状态仍按现有规则立即推送；
- `swept`、`graduated` 仍只对观察名单中的代币推送；
- 启动补扫只恢复状态，不发送历史 Telegram；
- blocked 风险候选进入完整深检后仍可按现有策略发送风险提醒。

本次不会使 V3/V4 获得普通推送，也不会降低 70 分或用户配置的其他门槛。

## 测试与验收

单元和集成测试覆盖：

1. Pons 身份识别调用官方 Provider，不调用 analysis Provider。
2. 官方身份读取出现可恢复错误时进入持久化延迟恢复，且不回退 Alchemy。
3. 永久错误和编程错误向上传播，不被记录为已处理。
4. Pons 候选仍进入原生命周期路径。
5. 非 Pons V3、V4 和未知场所被标记已处理，且不会调用完整分析函数。
6. 支持的 V2 候选仍可进入完整分析。
7. 确定上界低于 `max(0, MIN_SCORE - 10)` 的 V2 候选不调用完整分析。
8. 上界等于该深检线的候选继续深检，60–69 分范围的既有风险检查覆盖不减少。
9. 市场输入缺失或非法时预筛 fail-open，继续深检。
10. 实时候选、启动恢复和持久化候选恢复使用同一门控规则。
11. 跳过、深检和延迟计数准确，日志不泄露 RPC URL 或密钥。
12. Telegram 通知策略的现有回归测试保持通过。
13. analysis Provider 连续 429 后打开熔断；冷却期不再发出深检 RPC，发现游标仍推进。
14. 冷却结束只允许一次探测；成功关闭熔断，429 重新冷却。
15. 每个熔断周期只发送一次告警，日志和通知不泄露 URL 或 Key。
16. 非 429 的编程错误和永久错误不被熔断器吞掉。
17. Solana Provider 不接入 EVM 分流和熔断路径。
18. 完整运行 `npm test` 与 `git diff --check`。

建议部署后运行至少 12 小时，比较 `paid_deep_checks / 候选总数` 与 Dwellir 控制台响应数。验收目标是 V3/V4 候选不再产生付费深检，扫描器专用 Key 的月度 quota 为 20,000,000，同时 V2 合格候选和既有重要状态通知不受影响；不承诺固定节省百分比，因为候选构成会随市场变化。

## 文档

更新 README 的双 RPC 章节，说明：

- 官方 RPC 负责逐候选 Pons 身份识别且该路径不回退；
- Dwellir/Alchemy 等付费分析节点只负责通过场所门控和预筛的深检；
- V3/V4 目前只发现和去重，不执行付费深检；
- 四条 EVM 链必须共用一个设置了 20M 月度 quota 的扫描器专用 Dwellir Key，其他项目必须使用不同 Key；
- 路由统计是本地次数，不等同于供应商最终账单；真实额度以 Dwellir 控制台为准；
- analysis RPC 429 会触发本地冷却，但不会停止官方发现。

现有 `DISCOVERY_RPC_URL`、`ANALYSIS_RPC_URL`、`RPC_URL` 和 `MIN_SCORE` 语义不变，不新增本地月度额度配置。

## 非目标

- 不接入新的 RPC 服务商或供应商用量 API。
- 不改用 WebSocket，不调整发现轮询频率和日志区块范围。
- 不实现 V3/V4 卖出能力验证。
- 不改变评分分值、聪明钱规则、通知门槛或风险等级。
- 不增加交易、模拟交易、私钥或自动买卖功能。
- 不修改各链候选状态文件 schema，不升级依赖，不把 Solana 纳入 EVM 月度预算。
